# 文档分层与权威来源：docs/ 入库，.docs/ 只放过程

文档分两层，**`docs/` 是唯一真源**：Wiki 只做导读与 FAQ；过程材料放不入库的 `.docs/`。
每份内容型文档在头部写一行「最后核对：日期 · 对应版本」。

_Status_: accepted · 2026-11-21

## 背景

到 2026-11-21，仓库文档有三处结构性问题：

- **两层混用**：`docs/` 里放着 v1.1 的 UI 简报、技术核查、实施记录和两个可运行原型——这些是
  只对当期成立的过程材料，按 [AGENTS.md](../../AGENTS.md) 的文档分层规则应放在 `.docs/`
  （gitignore、不入库）。
- **入口分裂**：README 把使用文档指向 GitHub Wiki，但 Wiki 不随代码版本化，容易与实现漂移；
  同时 `docs/` 里又留着 DOCKER / PACKAGING / CAPACITY 这类使用文档。
- **状态标记失效**：文档头部写着「状态：v0.1 · 2026-11-01」却没有维护机制，
  [PROTOCOL](../PROTOCOL.md) 还标着「草案 v0.1」而实现早已越过它。

## 决策

1. **`docs/` 是唯一真源**。它入库、随代码版本化；Wiki 只承载导读、快速上手与 FAQ，
   不再放需要与实现同步的内容。
2. **过程材料不入库**。过程记录、实测证据、含内网 IP 或机器信息的材料放 `.docs/`。
   2026-11-21 已把 `docs/design/` 整体（12 份 Markdown + 两个 Avalonia 原型工程）迁到
   `.docs/design/`；迁移前把仍有效的契约要点吸收进了 [PROTOCOL](../PROTOCOL.md)。
3. **每份内容型文档写状态头**：文件前 6 行内一行
   `> 最后核对：YYYY-MM-DD · 对应 <版本号|未发版>`。日期含义是「最后一次确认该文档与实现一致」。
   例外：索引页（[docs/README.md](../README.md)）、ADR（用自身 `_Status_` 行）、
   [adr/TEMPLATE.md](TEMPLATE.md)。
4. **改代码的 PR 必须同改受影响的文档**。「文档未更新」可以作为拒绝理由。
5. **`docs/` 维持中文单语**。英文只保留 [README.en.md](../../README.en.md) 与
   [CODE_OF_CONDUCT](../../CODE_OF_CONDUCT.md) 指向的官网原文。

### 附：ADR-0002 的取代关系

[ADR-0002](0002-transport-per-media.md) 写于「传输模式由用户选择」时期。自 2026-11-03 起：

- **已失效**：模式由用户选择、客户端提供切换开关。
- **仍然有效**：三类媒体各自决定路径、文字永不走直连、v1 不做逐成员混合。

现行方案是**服务端配置决定策略**（`--voice-mode` / `--screen-mode`，默认均 relay），
客户端只消费 `transport`。见 [PRODUCT](../PRODUCT.md)「传输策略」与 [PROTOCOL](../PROTOCOL.md)。

## 后果

**正面**

- 读者只有一个入口，不会在 Wiki 与 `docs/` 之间遇到两个版本的同一份说明。
- 过程材料不再挤占公开文档面；`docs/` 的每一份都承诺当前有效。
- 「最后核对」日期让陈旧文档立刻可见，而不是靠读者猜。

**负面**

- 迁移把两个可运行原型移出了公开仓库，只能在 Git 历史里找回。
- 状态头靠人工维护；CI 只能检查它存在与格式，检查不了内容是否真的准确。
- 「改代码必须同改文档」依赖评审执行，无法完全自动化。

## 考虑过的方案

| 方案 | 为什么没选 |
| --- | --- |
| 保留 `docs/design/`，只加「历史设计」标记 | 规则与现状继续不一致，读者仍要自己判断哪份还有效 |
| 以 Wiki 承载使用文档、`docs/` 只放开发文档 | Wiki 不随版本走，同步成本高于收益 |
| 不做状态头，只靠 Git 提交时间 | 提交时间包含改错别字等无关修改，不能代表内容被核对 |
