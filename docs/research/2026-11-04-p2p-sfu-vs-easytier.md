# P2P + 兜底 SFU 与 EasyTier 的架构对比

> 2026-11-04。回答一个问题：PartyUp 的「P2P + 兜底 SFU」能不能参考 EasyTier 的架构？
>
> 结论先说：**策略层可以借鉴，传输层不能照搬。** 根本原因是两者承载的对象不同——EasyTier 换承载路径时上层无感，WebRTC 换路径必须重建会话。

## 两者在做什么

| | EasyTier | PartyUp |
| --- | --- | --- |
| 本质 | **三层网络隧道**（虚拟 IP 网络） | **带媒体协商的会议系统** |
| 承载内容 | 任意 IP 报文（TCP/UDP 字节流） | 音频帧（Opus）与视频帧（H.264/VP8），走 DTLS-SRTP |
| 路径决策 | 每个 peer 对独立、客户端自行机会性选择 | 服务端配置决定，同一频道同一媒体同一时刻一种路径（v1） |
| 换路径的代价 | 换承载，上层 TCP 连接不断 | 重建 PeerConnection：ICE 重启 + 重新协商 + 编码器重新适应 |

## EasyTier 的机制（依据源码复核，非文档描述）

以下细节在调研中据源码核实过，与直觉不同，一并记录：

- **中继是缺省数据路径，打洞是后台机会性重试。** 它没有「打洞失败 → 切中继」这种判定——流量一开始就走中继，同时后台每 5 秒收集候选并尝试直连，成功后**隐式升级** relay → p2p，直连一断立即回落到中继（旧中继不拆，降为备用）。退避 1s→16s（锥形 NAT）或 →64s（对称 NAT）。
- **STUN 采样与 NAT 分类**：每轮取「前 2 台 + 随机 1 台」，每台 3 个 BINDING 请求，≥2 台响应才做 NAT 类型分类；失败 10s 复测、成功 600s 复测。peer 内置 STUN responder，可以互当 STUN 用。
- **对称 NAT 的探测方式**：`HardSym` 由对端用生日攻击式随机端口表（1..65535 洗牌，每轮随机 600–800 端口 ×3 包，1ms/端口，本端 84 个 socket 并行收、按 transaction id 匹配）；`EasySym` 才是 ±50 区间扫描。
- **中继数据面默认为网络密钥整包 AEAD**，同一信任域内可解；只有 secure mode 才叠加逐会话 Noise 端到端加密。（因此「中继节点看不到内容」**只对 secure mode 成立**。）
- **直连失败 3 次**退避 1/2/4s 后拉黑 300s，每 5s 重扫 listener。
- CLI `easytier-cli peer` 的 cost 列直接显示 `p2p` / `relay(N)`，N 为跳数。

## 不能照搬的两点

### 1. relay-first + 后台机会性升级

这对用户体验确实更好：永远有可用路径，切换时上层无感。

但对 PartyUp 有三个不可接受的代价：

1. **媒体要发两份**（同时维护中继与直连两条路径），家用上行带宽扛不住——这直接违背「屏幕共享 1080p 优先」的规模目标。
2. **与「服务端决定传输策略」的产品原则冲突。** EasyTier 让客户端自行机会性选择路径；我们的设计里路径是部署者的配置，客户端无权也无需选择（见 `PRODUCT.md` 传输策略）。
3. **中继必须始终在线**，意味着服务器带宽按「所有人同时中继」估算，而不是按「兜底」估算。

### 2. 无缝切换

EasyTier 的隧道切换用户无感，因为上层是字节流。

WebRTC 做不到，而且**不应假装能做到**：一条 PeerConnection 只有一条传输路径，换路径必须重建会话，中间必然有 1–2 秒中断，编码器也要重新适应码率。

因此 PartyUp 的回落承诺是「自动恢复、不需用户操作」，**不是**「切换过程无感」。这个区别必须写进产品文案，否则用户会以为卡顿是 bug。

## 可以借鉴的四点

### 1. 候选收集的重试与拉黑策略

EasyTier 的「失败 3 次退避 1/2/4s 后拉黑 300s」比我们 v1 的「试一次、失败就切」精细得多。做逐成员混合时，这套机制能避免对明显不可达的对端反复尝试，节省时间与电量。

### 2. NAT 类型分类

「多台 STUN 采样 + ≥2 台响应才分类」的做法可以复用。判断出某成员是对称 NAT 后，可以直接跳过直连尝试（对称 NAT 对对称 NAT 基本打不通），把该对成员直接安排为中继——**省掉的是等待超时的那 10 秒**，这是用户实际感知到的延迟。

### 3. 成员中继（peer relay）

任意已连接的成员可以充当中继节点。这正是 PartyUp 未来的方向（见 `PRODUCT.md` 待决）。

技术上并不遥远：我们的 SFU 本质就是 RTP 转发，把同一个转发逻辑放到一个客户端上即可。难点不在转发，而在：

- 该成员的上行带宽（他要同时给多个人发）
- 谁来选中继、选中继失败怎么办
- 中继成员掉线时的重连

### 4. 路径成本的表达

`p2p` / `relay(N)` 这种表达可以直接用于路径历史：`直连` 比 `经服务器中继` 更「便宜」，将来有成员中继时可以显示 `经 alice 中继`。这让「当前走哪条路」不只是一个标签，而是一个可解释的成本。

## 对当前实现（v1）的影响

**不变。** v1 保持：

- 服务端配置决定策略（`--voice-mode` / `--screen-mode`，默认 relay）
- 不做 STUN 重试与 NAT 分类：候选收集失败即判定直连不可用
- 直连失败按**频道整体**降级为中继（不做逐成员混合）
- 降级后不自动升回（避免抖动），重启服务端才恢复策略原值

这些选择的价值是**可预测**：任一时刻路径都是确定的、可复现的、能写进日志解释的。EasyTier 的机会性模型换来更好的体验，但代价是不可预测——出问题时很难说清「为什么这次走了中继」。
