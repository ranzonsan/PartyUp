# 项目边界

> 四类边界。每条都指向**权威文档**；本文只做索引、判据，以及「越界之后怎么处理」。
> 边界不是建议，是**拒绝改动时的依据**。

## 0. 怎么用

- 收到一个需求或 PR：先按下表定位它属于哪条边界，再读对应的权威文档。
- 定位不到归属：按**产品范围边界**处理——默认不做。
- 认为边界本身有问题：走 [ADR](adr/) 流程改边界，不要夹在一个功能 PR 里悄悄绕过。

| 边界 | 管什么 | 权威文档 |
| --- | --- | --- |
| 产品范围 | 做什么、不做什么 | [PRODUCT.md](PRODUCT.md)「非目标」 |
| 架构与依赖 | 谁能调用谁、什么东西可以跨边界 | [ARCHITECTURE.md](ARCHITECTURE.md) §2 |
| 协作 | 谁来决定、怎么评审、AI 怎么参与 | [GOVERNANCE.md](../GOVERNANCE.md)、[CONTRIBUTING.md](../CONTRIBUTING.md) |
| 法律 | 许可、名称使用、安全披露 | [LICENSE](../LICENSE)、[TRADEMARK.md](../TRADEMARK.md)、[SECURITY.md](../SECURITY.md) |

## 1. 产品范围边界

**一句话**：PartyUp 是给 2–12 人小圈子用的自托管开黑工具，不是一个通用通信平台。

明确不做（详见 PRODUCT 非目标）：官方托管、无服务器模式、移动端、会议能力、
端到端加密、v1 里的逐成员混合路径与成员中继。

### 判据

一个需求只要**命中任意一条**，就属于越界：

1. 它要求**官方托管**、注册即用、或依赖外部账号体系。
2. 它把产品推向**会议工具**（日历、录制、举手、主持人转移、等候室）。
3. 它要求我们**看见媒体内容**才能实现（除中继转发本身）。
4. 它为**单一用户的部署便利**引入常驻云依赖。
5. 它需要在 v1 里做**逐成员**的路径决策——v1 的自动回落是按频道整体降级的。

### 已知代价，不是缺陷

- `direct` 语音硬上限 2 人，第三个人会收到明确拒绝。
- `direct` 屏幕共享只允许 1 个观看者。
- 以上几条不是 bug，是 [ADR-0002](adr/0002-transport-per-media.md) 与 PRODUCT 的选择；
  报「为什么第三个人进不来」时请引用判据，而不是当作缺陷修。

## 2. 架构与依赖边界

**一句话**：三条边界，跨过去只能传值和句柄，不能传对象。

| 边界 | 两侧 | 契约 | 允许过界的东西 |
| --- | --- | --- | --- |
| 2.1 | UI ↔ 媒体核心 | C ABI | 基本类型、不透明句柄、错误码、帧句柄 |
| 2.2 | UI ↔ 服务端 | HTTP + WebSocket | JSON 消息 |
| 2.3 | 媒体核心 ↔ 对端 / 服务端 | WebRTC | SDP、ICE、媒体包 |

### 依赖方向

- UI **依赖**媒体核心；媒体核心**不知道** UI 存在。
- 客户端与服务端**只通过协议**耦合：不共享源码、不共享模型类、不共享数据库 schema 假设。
- 服务端**不解析媒体内容**，只做转发与信令。
- 媒体核心**不做业务决策**：进哪个频道、能不能共享，由服务端与 UI 决定。

### 禁止的用法

- UI 直接处理 SDP / ICE（这些原样转给媒体核心）。
- 跨边界共享内存、对象引用或回调指针（句柄除外）。
- 服务端依赖某个客户端版本的具体行为。
- 为了少写一层，把媒体核心的逻辑搬到 C# 里重写。

### C ABI 变更规则

- **只增不改**：新增导出函数不破坏兼容。
- **破坏性变更**必须提升 `PU_ABI_VERSION`（当前 2，见
  `src/media-core/include/partyup_media.h`），并同步更新
  [ARCHITECTURE.md](ARCHITECTURE.md) 与 [PROTOCOL.md](PROTOCOL.md) 的兼容说明。
- 客户端加载 DLL 时校验 ABI 版本，不匹配就**明确拒绝**，不要试图容错。
- 构建产物（`src/media-core/out/`、`artifacts/`）不入库。

## 3. 协作边界

**一句话**：谁决定、怎么评审、AI 参与到什么程度，都有明文。

- **决定权**：BDFL，最终合并权归项目 owner（[GOVERNANCE.md](../GOVERNANCE.md)）。
- **不可逆决策**：先写 ADR，`accepted` 之后才能动代码。
- **AI 参与**：允许，但必须披露环节、能解释每一行、附真实跑过的验证
  （[CONTRIBUTING.md](../CONTRIBUTING.md)「AI 参与」）。
- **敏感路径**：`.github/CODEOWNERS` 列出了协议、ABI、鉴权、发布流水线等面，
  这些路径的改动一定会被 owner 看到。

## 4. 法律边界

**一句话**：代码是 GPL-3.0，名称与图标不是。

- **许可**：GPL-3.0。分发修改版必须同样开源，并保留版权声明。
- **名称与标识**：GPL 不授予名称使用权。对外分发**修改版**必须改名并替换图标，
  并在 README 首段说明与原项目无隶属关系（[TRADEMARK.md](../TRADEMARK.md)）。
- **安全披露**：漏洞走私密渠道，公开 issue 不接收细节（[SECURITY.md](../SECURITY.md)）。
- **无 E2EE 是设计选择**：`relay` 模式下服务端必然可见媒体明文，这不构成漏洞。
- **担保**：按 GPL-3.0 的免责条款，本软件不提供担保。

## 5. 边界怎么改

1. 开一个 issue，说明**哪条边界**、**为什么要改**、**不改变会怎样**。
2. 写 ADR，状态 `proposed`；涉及产品的同步改 PRODUCT.md，涉及架构的同步改 ARCHITECTURE.md。
3. ADR 变为 `accepted` 之后，才允许改代码。
4. 同一次改动里更新本文，保证索引与权威文档一致。

## 6. 越界怎么处理

- **issue**：关闭，引用具体条款，一句话解释。不进入长时间讨论。
- **PR**：关闭，引用具体条款；不做逐行 review——逐行 review 会被理解为「改小一点就能合」。
- **边界本身可疑**：按第 5 节走 ADR；不要在功能 PR 里夹带边界变更。
