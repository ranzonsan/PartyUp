# PartyUp 产品定义

> 状态：v0.1 · 2026-11-01。产品层决策已定稿；技术选型见 `docs/ARCHITECTURE.md`（待写）。

## 一句话

PartyUp 是一个自托管的桌面软件：**一台服务器、若干频道，频道里可以打字、说话、共享屏幕。**

## 目标场景

1. **开黑**：4–6 人，一边打游戏一边语音，偶尔有人共享屏幕给大家看结算画面或攻略。
2. **一起看东西**：1 人共享屏幕，1–3 人观看（看电影、看比赛、一起调试）。
3. **小圈子常驻**：几个人长期共用一个服务器，用邀请码加入，频道固定、历史保留。

## 非目标（v1 明确不做）

| 非目标 | 原因 |
| --- | --- |
| 官方托管 / SaaS | 只做自托管，见 [ADR-0001](adr/0001-self-hosted-only.md) |
| 无服务器（纯直连 / 局域网）模式 | 身份、历史、邀请码要另起一套设计，见 [ADR-0002](adr/0002-transport-per-media.md) |
| 摄像头视频 | 目标场景里没人需要；协议保留流类型位，不实现 |
| 移动端 | 桌面优先，Windows 首发 |
| 会议能力（日历、录制、主持人转移、举手） | 这是聊天工具，不是会议工具 |
| 端到端加密 | 与中继转发冲突，见下方「安全边界」 |
| 逐成员混合路径（同一通话里有人直连、有人中继）**及成员中继** | **v1 不做，是明确的未来方向**（见下方「待决」）。v1 的自动回落按**频道整体**降级，就是为了不做半吊子的逐成员实现 |

## 核心概念

完整定义见 [GLOSSARY.md](../GLOSSARY.md)。这里只给最短版本：

- **Server（服务器）**：一次自托管部署，拥有自己的成员、频道与历史。
- **Member（成员）**：在某个 Server 上注册的身份，不跨 Server。
- **Channel（频道）**：Server 内的房间，同时承载文字区、语音区、共享区。
- **Session（会话）**：一个客户端连上某个 Server 的一次生命周期。

## 传输策略

三类媒体各自决定路径。**路径由服务器的部署策略决定，客户端无权也无需选择**——用户不需要理解 NAT、不需要知道什么叫 SFU，装好就能用。

| 媒体 | 默认路径 | 决定方式 | 自动行为 |
| --- | --- | --- | --- |
| 文字 | 中继 | 固定 | 无 |
| 语音 | 中继（最多 12 人） | 服务端配置 `--voice-mode=relay\|direct` | direct 下直连失败 → 回中继（v1 之后）；**direct 语音硬上限 2 人**（第 3 人收到明确拒绝，见下方「已知代价」） |
| 屏幕共享 | 中继 | 服务端配置 `--screen-mode=relay\|direct` | direct 下直连失败 → 回中继（v1 之后） |

四条约束：

1. **路径不由用户选择**。客户端只消费服务端下发的 `transport` 字段，界面只读显示当前路径，不提供切换开关。
2. **v1 不做逐成员混合**。同一频道、同一媒体在同一时刻只有一种路径——所以直连失败时是**整个频道**降级为中继，而不是只把连不上的那个人切走。逐成员混合（含成员中继）是未来方向，见「待决」。协议上 `transport` 已按**成员**下发（v1 服务端让所有人取值相同），将来改成逐成员只需改服务端策略，不必重设计协议。
3. **服务器策略是唯一决定源**。同一服务器上所有频道共享同一策略；要换路径就改部署配置并重启，不改客户端。
4. **文字永不走直连**。没有服务器的路径意味着身份、历史、邀请码全要另起一套设计。

这样设计的三条理由：

- **用户不该为基础设施买单**。选择直连还是中继需要理解 NAT 类型、上行带宽、人数规模——这是部署者的事，不是开黑的人该操心的事。
- **双路径最怕"说不清走哪条"**。路径从两处（用户 + 自动回落）都能改，出问题时无法定位。收敛到服务端后，任一时刻路径都是确定的、可复现的。
- **部署者可为自己的人优化**。局域网自托管选 direct 省带宽，公网 VPS 选 relay 保连通性，一个配置项解决。

已知代价 1（**direct 语音硬上限 2 人**）：`--voice-mode=direct` 用 P2P，单人之间直连；**第 3 个成员进语音会被服务端明确拒绝**，提示「当前服务器配置为直连模式，语音最多 2 人；需要更多人请让管理员用 --voice-mode=relay 重启服务器」。文字聊天不受影响。不做成「能进但互相听不到」的静默降级——那会让用户以为产品坏了却查不出原因。

已知代价 2：**`--screen-mode=direct` 的屏幕共享只支持 1v1 观看**。P2P 下共享者要为每个观看者各建一条连接，第三人开始看不到（mesh 尚未实现），且共享者要**为每个观看者各编一份、各发一份**（libwebrtc 的一条 track 只能挂一个对等连接）。因此**默认路径是中继**（多人观看经服务端 SFU 转发）；显式选 direct 的部署者要接受 1v1 限制——界面已标注「直连（P2P，仅支持 2 人观看）」，不靠回落掩盖。

## 安全边界

传输本身用标准 WebRTC 加密（DTLS-SRTP），逐跳有效。但**媒体在服务器上解密后转发**：服务器管理员能看到语音与屏幕内容。v1 不承诺端到端加密，产品文案与文档都必须这么写，不能暗示"服务器也看不到"。

## 部署

- 只做自托管：一台能跑二进制的机器（VPS、家里 NAS、闲置电脑）。
- 理想形态：一个安装包 / 一条命令起服，数据落在本地目录，备份 = 拷目录。
- 不强制外部数据库、不强制域名与证书才能跑起来（局域网 IP 可用）。

## 规模目标

| 维度 | 目标 |
| --- | --- |
| 单频道同时在线 | 2–12 人（典型 4–6）；**12 人也是语音上限**——`sfu.MaxRemoteSlots` 是「发布者→槽位」的全局映射，12 个槽位 = 12 个语音成员，第 13 人进语音会被明确拒绝（文字不受影响） |
| 单服务器同时在线 | ≤ 50 |
| 单频道同时共享 | 最多 2 路，每人最多 1 路 |
| 视频分辨率 | 屏幕共享按采集原生分辨率（默认不缩放），弱网降帧不降分辨率 |

## v1 验收

按顺序，全部可手工验证：

1. 一条命令起服，首次启动打印邀请码。
2. 第二台机器用邀请码加入，成为成员。
3. 两个客户端在同一频道互发文字，重启服务端后历史仍在。
4. 双方进入语音区，能听见彼此；第三人加入仍能听见。
5. 屏幕共享：服务端配 `direct` 时 1v1 可看；配 `relay` 时多人可看。
6. 拔网线 5 秒再恢复，语音自动重连，不需要重进频道。
7. 界面上能看到每一路流**当前走的是直连还是中继**，以及**路径变化历史**（何时、从哪条到哪条、为什么）。

第 7 条是产品差异点：双路径设计最怕"说不清现在走哪条"。路径变化只有两个来源，界面必须都能解释清楚：

| 变化来源 | 是否用户发起 | 界面必须显示 |
| --- | --- | --- |
| 服务端策略变更（重启后换了 `--voice-mode`） | 否 | 新路径 + 「服务端策略变更」 |
| 直连失败自动回落到中继 | **否** | 新路径 + 「直连超时/失败，已自动回落」 |

第二类是重点：**系统替用户做了决定，不告诉他就只会表现为"刚才卡了一下"**。没有这条记录，双路径系统就退化成"时好时坏的玄学"。

## 待决

- 客户端技术栈（GUI 框架 + 媒体库接入方式）——决定后写 `docs/ARCHITECTURE.md`。
- 服务端进程模型（单进程 vs 控制面与媒体面分离）——同上。
- 更新机制（自动更新 / 手动下载）。
- **逐成员混合路径 + 成员中继（v1 之后的主要方向）**：同一通话里，A 与 B 可以直连、A 与 C 走服务器中继，甚至由某个成员充当中继节点。这要求 ① 每个对端一条独立会话（mesh 或选择性 P2P + SFU 混合）；② `transport` 按**成员对**而非按频道表达；③ 界面能显示"我和谁直连、和谁走中继"。
  **v1 的架构必须不挡这条路**：`voice.state.members[].transport` 已按成员下发（v1 服务端让所有人取值相同），将来改这一层时不必重设计协议。
