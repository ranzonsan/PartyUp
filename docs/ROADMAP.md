# PartyUp Roadmap

> 最后核对：2026-11-21 · 对应 未发版

> 这份文档记录 v1.0 的验收判据与当前进度，不是产品承诺。
> 产品级事实以 `docs/` 下的文档为准；这里只回答「v1.0 还差什么、怎么算做完」。

## 0. 基线（2026-11-08）

- 版本与发布通道已拆分：客户端 `client/VERSION` 对应 `v*` tag，服务端 `server/VERSION`
  对应 `server-v*` tag，容器镜像跟随服务端通道。
- 已产出：客户端 `v0.1.0`（draft）、媒体核心 `media-core-v2.19.0`（ABI v2，43 个导出）。
- `direct` 模式目前是硬 1v1：语音最多 2 人，第三人被明确拒绝；屏幕共享只允许 1 个观看者。
  多人（3–12 人）目前只能走 `relay`。

## 1. 「v1.0」的定义

不是功能多，而是**别人能拿去当日常工具**：

1. 陌生人按 README 能在 10 分钟内把服务端跑起来（Docker 或 Windows zip）；
2. 客户端装上就自动更新，不需要手动下载下一版；
3. 下载页提供 **SHA256 校验值**，并写明怎么核对；
4. 3 人以上语音与看共享是稳的（有实测数据，不是「应该可以」）；
5. 协议、容量、部署文档齐全，出问题能自己查。

## 2. v1.0 之前必须完成（按优先级）

### P0-1 一份编码、多路分发的 P2P 广播

**要解决的问题**：现在 direct 只能 1v1。libwebrtc 的一条 `VideoTrack` 只能挂一个
`PeerConnection`，N 个对端就要 N 份编码（CPU 与上行都线性增长，见
[桌面 GUI 与媒体栈调研](research/2026-11-01-desktop-media-stack.md)）。目标是：
**发送端只编码一次，把同一份编码结果分发给 N 个直连对端**，从而支持「3–6 人的小群 P2P 广播」。

**验收判据（可测，不是感觉）**

| 项 | 判据 |
|---|---|
| 编码次数 | 4 人频道共享，编码线程数 / 平均 CPU 编码占用 ≈ 1 份（对照现有 1v1 的数值 ±20%） |
| 功能 | 4 个客户端同时观看同一路共享，全部出画；语音 4 人互听 |
| 隔离 | A 停止观看不影响 B、C 观看（对照接收隔离语义） |
| 弱网 | 单路 RTT > 200ms 或丢包 5% 时，只有该路降级，其他人不受影响 |
| 稳定性 | 30 分钟连续共享 + 中途进出人，无崩溃、无黑屏超过 2s |
| 上限 | `DirectMaxMembers` 从 2 提升到至少 4，且是实测支撑的数字 |

**三条候选技术路线（先选型，再写代码）**

- **R1：Simulcast/SVC + 自建转发**——发送端按层编码（1 份 → 多个空间层），每个对端按自己
  带宽订阅不同层。libwebrtc 的 simulcast 是为 SFU 设计的；直连时没有 SFU 帮忙选层，需要
  自己实现「按对端选层 + 切层关键帧对齐」。
- **R2：编码输出复用（encoder fan-out）**——用 custom `VideoEncoder` 把编码后的帧同时喂给
  多个 `RtpSender`。libwebrtc 公开 API 不直接支持；要么改 `VideoStreamEncoder`/`RtpVideoSender`，
  要么在 native 层自己组包/发 RTP。这是「一份编码多路分发」最贴合的实现路径，但侵入最深
  （需要自己维护 libwebrtc 补丁）。
- **R3：选择性 P2P + SFU 混合（过渡）**——≤2 人直连、≥3 人自动中继。成本最低，但不算真正的
  「P2P 广播」，只能作为 R1/R2 未落地前的兜底。

**建议顺序**：先做 R3（1–2 天，消除「第三个人被拒」的体验硬伤）→ 再评估 R2（需要改
libwebrtc，估 2–4 周，含真机验收）→ R1 作为 R2 的备选。

**里程碑**

- M1 技术选型报告 → 已完成；结论摘要见
  [P2P 广播选型摘要](research/2026-11-13-p2p-broadcast.md)
- M2 native 层 PoC：单路编码 → 2 个 PeerConnection 分发（命令行探针，不接 UI）
- M3 服务端与协议：`DirectMaxMembers` 提升、`transport` 按成员对表达、第三人不降级
- M4 客户端接入 + 4 人真机验收（按上表判据）

**风险**

- 编码器 fan-out 会碰 libwebrtc 内部结构，**升级 libwebrtc 版本时补丁会反复冲突**；
- 每路独立拥塞控制（发送端要为每个对端维护 pacer/重传缓冲），复杂度高；
- 关键帧请求（PLI）来自多个对端时要不要合并，处理不好会编码抖动；
- 若最终只做 R3，产品文案必须写明这是中继而非广播。

**选型结论**：M1 报告的结论是「没有可直接依赖的开源实现」，并新增了一条更务实的
**R5（发送端本地 SFU helper）**路线。完整对比与推荐见
[P2P 广播选型摘要](research/2026-11-13-p2p-broadcast.md)。

### P0-2 自动更新端到端验证

现状：代码已接 Velopack，但从未在**真实安装版**上验证过「检测到新版 → 下载 → 重启 → 版本变了」。

- 判据：装 0.1.0 → 发 0.1.1 → 旧客户端启动后收到提示 → 点更新 → 重启后 `--version` 为 0.1.1；
  失败要能回滚（portable zip 兜底）。

### P0-3 容量实测（3–12 人）

现状：[容量基线](CAPACITY.md) 的部分数字是推算，不是实测。

- 判据：一台上行 30 Mbps 的机器，12 人 relay 语音 + 1 路共享，服务端 CPU/带宽/丢包有实测表；
  4 人、8 人各一组。

### P0-4 文档收口

- README 配图；
- `direct` / `relay` 的能力边界写清楚（现在散在 PRODUCT / PROTOCOL / CAPACITY 三处）；
- 故障排查表：文字能连但语音连不上、ICE 端口、防火墙、bridge 网络。

### P1（可进 v1.0 也可延后）

- 服务端管理面板的「可升级到新版本」提示（读 GitHub latest release，可开关）；
- 日志收集/导出（用户反馈问题时的取证成本）；
- macOS/Linux 客户端（架构跨平台，但媒体与 UI 都要重做，**不进 v1.0**）。

## 3. v1.0 之后（明确不进 v1.0）

- 摄像头视频；
- 端到端加密（E2EE）——与 SFU 冲突，要另设计；
- 服务器联邦（多服务器互通）；
- 移动端；
- 服务端录制/回放。

## 4. 明确不做

- 自研 TURN（用现成实现，或让部署者配 coturn）；
- 自研 SFU 之外的信令网关/媒体网关；
- 商业化功能（订阅、计费）；
- 购买代码签名证书。免费的第三方签名方案要求发布者署名为对方机构、并附加非商业与
  维护条件；付费方案对当前阶段不划算。v1.0 改为在下载页提供 SHA256 校验值。
