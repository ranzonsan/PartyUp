## 已放行：阶段A（身份与成员）

1. `POST /api/invite/validate`：JSON body传code，成熟解码/既有规范化；有效200、无效404、已用409。只读，不建账号、不消费码；最终注册仍事务内原子重验。不是用注册请求做预检，不额外使用GET路径传邀请码。
2. display_name独立于唯一登录name：注册可选、旧请求兼容，旧成员回退name；members表迁移可重启/幂等，旧字段语义不改变。名字不当身份ID。
3. 认证后的全服名册/状态：所有成员含离线；同成员多WebSocket聚合。空闲=在线而未入语音，不是键盘闲置。不能把文字订阅等同语音位置，不能静默只取一个频道掩盖实际多位置。
4. 单连接断开/退订不得误清其他连接仍持有的语音/共享状态。最后连接离开时完整清理。
5. 订阅初始共享快照。**语音快照已经存在**于[实际handler](<../../server/internal/server/hub.go#L653-L660>)，不要因只看subscribe helper而重做。
6. 增补对应store/server/protocol测试与[协议文档](<../PROTOCOL.md>)；敏感hash/token等不进入名册。

测试门槛：有效/无效/已用预检不改成员数/用码状态，预检后竞争注册重验；display_name旧库迁移/重开、旧新请求和响应；未认证名册拒绝、多连接聚合/断连保留；晚加入的语音/共享状态不依赖后来再发生事件。阶段A通过不等于完整UI接线或B/C完成。

## 待复核：阶段B（单流观看）

需要真实viewer意图、选择/停止转发与接收、relay/direct路径，以及目标和代次归属。不以隐藏画面或桩返回成功冒充停看。

- 新client能力协商与旧client自动绑定行为必须明确；新client+旧server/DLL不能假装支持。
- 一个viewer一次一路不等于一个共享者只能有一个viewer。不能未经产品/实现核查就新增“第二direct观看者一律CONFLICT”的限制。
- epoch必须绑定目标/回调生命周期；不能在旧帧回调到达时读新全局epoch重新贴标。切源/停止/重连的迟到帧须丢弃。
- 不为一次一路自动扩成通用多流解码框架，不改变两类direct/relay由服务端独立裁决的规则。

## 待复核：阶段C（音频能力）

复用实际通话的同一ADM，不另造独立录音栈。需要枚举/选择/默认跟随、热插拔/错误回退、本端电平与必要测试接口；全局PTT键、托盘属于客户端系统接入，不混算内核交付。

- 当前ADM有RecordingDeviceName/SetRecordingDevice/SetPlayoutDevice等，不能凭名称假设有GetSignalLevel。
- [AudioTrackInterface](<../../third_party/libwebrtc/include/api/media_stream_interface.h#L294-L308>)确实声明GetSignalLevel，但它是非纯虚的可失败interface；必须验证本端实际实现/数值更新，不能失败时填0冒充有效电平。
- 新导出需能力探测、结构布局/旧DLL组合验证；不因加法导出就直接承诺ABI兼容。
- 设备枚举/选择不等于允许偷偷入频道或对外发测试音。真实采集/桌面采集测试须明确，不能盲用会捕获整桌面的构建脚本`-Run`。
